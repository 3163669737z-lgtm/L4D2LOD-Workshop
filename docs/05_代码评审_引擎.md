### P1-1【实测】SMD 源跨目录同名 → 第二个模型静默不做 LOD（计划显示成功）

**位置**：`src/Engine/Batch/BatchPlanner.cs:301-311`
```csharp
if (pm.IsSmd) {
    srcPath = Path.Combine(AppInfo.TempSmdDir, pm.BaseName + "_src.glb");
    dstPath = Path.Combine(AppInfo.TempSmdDir, pm.BaseName + "_lod" + level + ".glb");
    finalPath = Path.Combine(pm.Dir, pm.BaseName + "_lod" + level + ".smd");
}
if (!dstSeen.Add(dstPath)) { log(LogLevel.Warn, "输出路径重复，跳过：" + dstPath); continue; }
```
**触发**：工程中存在两个不同目录、**basename 相同**的 `.smd`（真实工程里极常见：`characters/zoey/body.smd`、`characters/louis/body.smd`，或多个 `props/*/**body**.smd`），且被同一批 QC 引用（同 QC 或不同 QC 都会进同一个 `modelOrder` 循环）。
**后果**：临时 GLB 路径只由 `BaseName` 决定 → 第二个模型的全部级别被 `dstSeen` 丢弃；`PlannedModel.Jobs=0`、`SkipReason=null`。计划汇总时该 QC 仍有其它模型可做 → `Action=Process`；注入的 `$lod` 只含第一个模型的 `replacemodel`。第二个模型**没有任何 LOD、没有跳过原因、没有错误**，`--plan` 退出码 0。用户只会在日志里看到两条 `输出路径重复，跳过：…\smd\body_lod1.glb`（还暴露内部临时路径），很容易忽略。
**证据（T3）**：
```

[提示] 输出路径重复，跳过：C:\Users\…\Temp\L4D2LOD远景工坊\smd\body_lod1.glb
[提示] 输出路径重复，跳过：C:\Users\…\Temp\L4D2LOD远景工坊\smd\body_lod2.glb

  model dir=a jobs=2 skipReason=

**修复建议**：
1. 临时文件名改为**唯一**：`BaseName + "_" + SHA1(GetFullPath(pm.Path)) 前 8 位`，或直接 `TempSmdDir\<路径哈希>\<BaseName>…`（每模型独立子目录）。

### P1-2【实测】SMD 顶点不带 links 时，LOD 所有顶点被绑到 bone 0（无警告）

**位置**：
- `src/Engine/Model/GlbCodec.cs:488`：`bool skinned = bones.Count > 0 && model.HasSkinWeights;`
- `src/Engine/Model/SmdGlbCodec.cs:208`：`if (!skinned) return vertex;`（不写回 `vertex.Bone`，因为 GLB 无 Joints 可取）
- `src/Engine/Model/ModelContracts.cs:28-36`：`SmdVertex.Bone` 的语义注释明确“无 links 的顶点靠它绑定骨骼；写出时 Weights 为空则用本字段”——但转换链路把该字段丢了。

**触发**：源 `.smd` 有 `nodes`/`skeleton` 段，但顶点行是 9 字段（只有主骨骼索引、没有 links 数量与权重）。SMD 格式允许这种写法（单骨骼刚性绑定），旧规格 `spec_smd_glb.md` 的 A1/V3/V4 也专门讨论过。
**后果**：`HasSkinWeights=false` → SMD→GLB 不写 skin → Blender 按静态网格处理 → 回写 SMD 时 `SmdGlbCodec.BuildVertex` 提前 `return vertex`，`vertex.Bone` 保持默认 0 → 输出 LOD 的所有顶点首字段=0、links=0。骨骼表还在（nodes/skeleton 照抄），但**所有顶点绑到骨骼 0**：角色的 LOD 在动画里会整体僵在根骨骼（近看正常、远看错位/撕裂）。整个过程**没有任何 warning**（`WeightlessVertices` 只在 skinned 分支统计）。
**证据（T10）**：
```
原始 SMD：nodes 有 root(0)/spine(1)；顶点行以 1 开头（主骨骼=1）
--batch 结果：exit=0  BATCH: OK · 1 QC 写入 · 2/2 减面成功
LOD1 顶点行主骨骼分布: 0x540   ← 540 个顶点全部 bone 0
LOD1 样例顶点行: " 0 0.000000 0.000000 0.000000 0.000000 0.000000 1.000000 0.000000 0.000000 0"
LOD1 nodes 段: version 1 | nodes | skeleton | time 0
```
**自测覆盖**：**无**。`模型：SMD 解析容错（9 字段/空白/坏行/CRLF/LF）` 只测解析；`模型：SMD→GLB→SMD 往返（几何/UV/权重/骨骼索引）` 用的是带 links 的权重。没有“有 nodes、无 links”的往返用例。
**修复建议**：
1. `skinned = bones.Count > 0 && (model.HasSkinWeights || 任一顶点 Bone 能映射到骨骼列表位置)`；无 links 的顶点写 `WEIGHTS_0 = {1,0,0,0}`、`JOINTS_0 = {bonePosition,0,0,0}`（bone 无法映射时回 0 并计数）。
2. 无论如何在 `BuildVertex(!skinned)` / `WriteFromSmd` 里对“有 bones 但没写出 skin”输出 warning（`SmdGlbCodec` 已有 Warnings 通道）。
3. 新增自测：`模型：SMD 有 nodes 无 links → LOD 顶点仍绑定原主骨骼`。

### P1-3【实测】混合换行 QC：第二次运行把**全文**换行统一（违反“保留换行 / 幂等”）

**位置**：
- `src/Engine/FileUtil.cs:261-265`：`DetectNewLine` 只要出现一处 `\r\n` 就判整文件 CRLF。
- `src/Engine/Qc/QcLexer.cs:148-170`：`TryRemoveToolBlock` 先 `text.Replace("\r\n", "\n")` 再把所有行 `string.Join("\n", …)` —— **整篇归一化**。
- `src/Engine/Qc/QcWriter.cs:341-355`：擦除旧块后，因为 `rootFile.NewLine == "\r\n"`，把**整个 cleaned 文本** `.Replace("\n", "\r\n")`。

**触发**：QC 文件是“混合换行”（例如主体 LF、仅某一行/块是 CRLF；老版本编辑器、git autocrlf、跨工具复制都容易产生）。第一次运行只影响追加的块（块用检测到的 CRLF），主体 LF 被保留；第二次运行擦块时整篇转成 CRLF。
**后果**：第二次运行 **并非幂等**：工具块之外的用户内容换行被改写（本次实测 5 处 LF→CRLF，文件 607→612 B），同时多产生一份带时间戳的备份（`.lodbak_MMddHHmmss`）。违反 `docs/00 §4.1.6`“写回沿用原编码/BOM/换行”和验收 F-03“连续跑两次产物字节级一致”。内容语义不变、可还原，但对“量具/安全工具”而言是对用户文件的计划外改写，且会让 diff/版本控制出现噪声。
**证据（T2）**：
```
mixed.qc 原始：5 行 LF + 末行 CRLF（117 B）
run1 后：607 B，CRLF=18，裸 LF=5（工具块 CRLF，用户 5 行 LF 原样）
run2 后：612 B，CRLF=23，裸 LF=0，hash 改变；内容除换行外相同: True
run3 后：hash 与 run2 相同（稳定）
备份：mixed.qc.lodbak、mixed.qc.lodbak_1115185628（run2 额外产生）
```
**自测覆盖**：**未覆盖混合换行**。`QC：编码/BOM/换行读写保持` 只测“纯 CRLF / 纯 LF”；E2E 幂等用例的 fixture 是纯 CRLF。
**修复建议**：

2. 或更简单：检测到混合换行时，只做“按行偏移裁剪工具块区间”的字节级操作（不重建全文）。

### P2-1【实测】UTF-8 BOM + 非 UTF-8 正文（或 UTF-16 文件）：非法字节被 U+FFFD 替换并**写回**

**位置**：`src/Engine/Qc/QcTextFile.cs:76-115`（BOM 分支 `encoding.GetString(bytes,3,…)` 非严格；无 UTF-16 BOM 处理；失败回退 GBK/Default 也是替换式解码）。
**触发**：文件以 `EF BB BF` 开头但正文不是合法 UTF-8（例如 BOM 被错误地加到 GBK 文件上——转换工具/脚本事故）；或 UTF-16LE/BE 的 QC（`FF FE` / `FE FF` 不被识别）。
**后果**：非法字节被解码为 U+FFFD，写回时按 UTF-8 重新编码 → 原中文注释字节**永久改变**（实测 13 个 U+FFFD）；`.lodbak` 保留原始字节，因此默认配置可还原；**关闭备份则不可恢复**。UTF-16 QC 因解析不出 `$modelname` 一般不会被写（作为 include 文件被 force 注释时仍有风险），属“静默不支持”。
**证据（T9）**：原 115 B，含 GBK 中文注释；`--batch` 后 630 B；注释行变为 `// ����ע�ͣ�GBK �����ע��`（13 个 U+FFFD）；`.lodbak`=115 B 与原文件一致。
**自测覆盖**：**无**（`QC：编码/BOM/换行读写保持` 只测合法 UTF-8/GBK）。
**修复建议**：BOM 分支也用 `new UTF8Encoding(false, true)` 严格解码；失败时**不要静默替换**——记 warning 并拒绝写该 QC（`QcInfo.ReadFailed/Error`），或在“原文可能不可逆”时只允许工具块追加而禁止整篇重建。增加 UTF-16 BOM 检测（要么支持，要么明确拒绝并提示）。

### P2-2【实测】只读 QC 不会被拒绝：通过 Move 兜底覆盖、丢属性、遗留 `.old_*`

**位置**：`src/Engine/FileUtil.cs:20-78`（`File.Replace` 失败 → `File.Move(target, old)` + `File.Move(tmp, target)`）；`FileUtil.cs:80-83` 的 `TryDelete` 静默失败。
**触发**：QC 带 `FILE_ATTRIBUTE_READONLY`（用户手动只读、Perforce 等工作区常见）。

int culprit = (o.Current >= 0 && o.Current < pending.Count) ...
```
`o.TimedOut=true` 且 `o.SawStart=false`（例如 Blender 卡在启动/加载插件、GPU/驱动挂起、被安全软件拦截）时，不进入“整批失败”分支 → 只失败 `pending[0]` 并重启新进程；新进程大概率同样卡住 → 一个大工程（100 个任务）可能以“每任务 20 分钟 + 大文件加时”的速度失败，用户看到的是数小时“无进度”。（正常 `SawStart` 后卡住属预期路径，本问题只针对“脚本从未跑起来”的组合。）
**自测覆盖**：`Blender 后端：看门狗（空闲超时只失败卡住的任务…）` 用 `L4D2LOD_TEST_SLEEP` 模拟“脚本已启动后卡住”，不覆盖“启动阶段超时”。
**修复建议**：`if (!o.SawStart)` 不论是否 TimedOut 都走整批失败（或最多重试 1 次），错误文案给“Blender 启动后长时间无输出（可能是插件/驱动/安全软件问题）”。

### P2-14【实测】深嵌套 JSON 的损坏/恶意 GLB：`--plan` 统计面数时 **StackOverflow 崩溃**（进程直接终止，无报告/无 crash log）

**位置**：`--plan`/计划阶段对 GLB 只调 `GlbCodec.CountTriangles`（`GlbCodec.cs:395-463`）→ `GlbJson.SplitGlb`（`GlbJson.cs:51-119`）→ `Json.Parse`（`Json.cs:89-105`）→ 递归 `ParseValue/ParseObj/ParseArr`（`Json.cs:175-235`），**无深度上限**。
**触发**：用户工程里有一个 JSON 深度极大的 `.glb`（损坏或恶意构造；本次用 6 万层数组）。
**后果**：`StackOverflowException` 无法被 catch（`Main` 的 `try/catch` 与 `TryWriteCrashLog` 都拦不住）→ 进程直接退出（实测 exit `-1073741571`，stderr `Process is terminated due to StackOverflowException.`），计划 JSON 未生成、没有崩溃日志、GUI 无提示。发生在任何写盘之前，**不会损坏数据**，但属“进程失控 + 无诊断”。
**自测覆盖**：`模型：损坏输入抛出可读异常` 覆盖了截断/魔数/版本/sparse/索引，但没有“深嵌套/超大 JSON”压力用例。
**修复建议**：`Json` 解析器加 `MaxDepth`（如 512）并抛 `JsonException`；`SplitGlb` 再加 JSON 文本长度上限（如 64 MB）；这是 20 行以内的防御，建议优先做。

### P2-15【静态】`KillAll` 在 UI 线程逐个 `WaitForExit(3000)`：异常时界面最长冻结 24s；Kill 失败静默

**位置**：`src/Engine/Blender/BlenderScheduler.cs:75-88`；调用方 `ShellViewModel.cs:875-882`（`RequestStopInternal`，UI 线程直接调用）、`ShellWindow.xaml.cs:190-194`。
**触发**：停止/关窗时（自动并行上限 8 个进程，手动最多 16）。
**后果**：先对全部进程 `Kill()`，再**顺序** `WaitForExit(3000)`。正常时被杀进程毫秒级退出；但若某个进程进入不可杀状态（驱动/权限/挂起），“每个 3s × N”会让 UI 线程卡住（8 进程最坏 24s，手动 16 进程 48s），用户以为程序卡死；`Kill()` 异常被吞掉且无日志，若 `JobObject.Assign` 失败过，该进程可能残留。
**自测覆盖**：`Blender 后端：取消（KillAll 立即杀进程、无残留进程）` 覆盖正常路径。
**修复建议**：`KillAll` 改为“先 Kill 全部 → 用总预算（如 3s）轮询 `HasExited`”，并记录未能结束的 PID/错误；UI 调用改为后台线程/异步（不要阻塞 Dispatcher）。

### P2-16【静态】取消发生在“SMD 转换前置循环”时直接 return：不写报告、不清理临时文件

**位置**：`src/Engine/Batch/BatchRunner.cs:114-118`：
```csharp

    if (cancel.IsCancellationRequested) { outcome.Cancelled = true; return; }   // ← 无 WriteReports、无 temp 清理
```
**触发**：用户在 SMD→临时 GLB 转换阶段点停止（大 SMD 工程可能持续几十秒）。
**后果**：与其它取消路径不同，本次运行**没有报告/日志文件**（`WriteReports` 在 `:159/:262/:464` 三处调用，这条路径都没有），临时 GLB 残留到下次启动清理；UI 侧仍会显示“已停止”，但“打开报告”无内容。
**自测覆盖**：无。
**修复建议**：把取消/异常路径统一收敛到 `finally`（报告 + `TempCleanup`），或在该 return 前调用 `WriteReports` 与清理。

25. **包装 QC 命名与用户文件冲突**：`ProjectScanner.cs:196-200`（`自动LOD_` 前缀被当作工具产物）→ 用户自己的 `自动LOD_x.qc` 会被当作工具文件；`EnsureWrapperQc` 对同路径文件“沿用不覆盖”是好设计，但计划阶段若判断“已存在”则解析的是**用户文件**，工具会往里注入 `$lod`。低概率，记录。
26. **`OldSeparateQcToDelete` 宽松匹配**：`BatchRunner.cs:497-513`（根 QC 文本里只要出现 `"sep2_LOD.qc"` 字样（不要求在工具块内）、且目标文件头含“自动 LOD 工具/远景工坊”字样，就删除该文件）→ 用户手工 include 的同名文件可能被删。修：仅当工具块内确有该 include 行时删除。

**日志 / 报告**
27. **`RecordingObserver`/`BatchOutcome.LogLines` 无上限**：`BatchRunner.cs:580-617`；UI `LogViewModel` 有 4000 行上限（`LogViewModel.cs:62`）。→ 超长运行的报告/日志内存无界（每个任务成功也至少 1-2 行；10 万任务级才会成问题）。修：报告侧截断并写“省略 N 行”。
